### SEC-001 予測可能な一時ファイルから別ファイルを上書きできる

初回調査時は未修正。現在はPR #73で修正・マージ済み。CWE-377 / CWE-61に相当する。

対象は [internal/filewriter/filewriter.go](../../internal/filewriter/filewriter.go) の18行、23行、28行、32行。

`WriteAtomic` は一時ファイル名を `.<basename>.pedit-<PID>.tmp` と決め、`os.WriteFile` で開いている。排他的な新規作成になっておらず、同名のシンボリックリンクがあればリンク先を開いて切り詰める。続く `os.Chmod` もリンク先に作用する。最後の `os.Rename` はリンクそのものを共有ファイルの名前に移す。

攻撃者が共有ディレクトリなどの保存先にファイルを作成でき、CLIのPIDと共有ファイル名を把握できる場合、共有対象外のファイルをリンク先に指定できる。リンク先への書き込み権限が必要なのはCLIの実行ユーザーであり、攻撃者自身ではない。リモートの招待リンクだけで成立する攻撃ではない。

影響は、CLI実行ユーザーが書き込める別ファイルの内容破壊、およびその権限の変更である。共有ファイルがリンク化すると、以後の読み書きもリンク先へ向かう。攻撃者が共同編集にも参加していれば、書き込まれる内容を操作できる。

再現は [filewriter_test.go.txt](repro/filewriter_test.go.txt) の `TestSecurityAuditPredictableTempSymlink`。テスト専用ディレクトリ内で次を実行した。

1. `notes.md` を0644、別ファイル `private.txt` を0600で作成する。
2. 現在のPIDから一時ファイル名を組み立て、`private.txt` へのリンクを置く。
3. `WriteAtomic(notes.md, "peer controlled update")` を呼ぶ。
4. `private.txt` の内容が置換され、権限が0644になり、`notes.md` 自体がリンクになったことを確認する。

修正案は、`os.CreateTemp` などで排他的に作成したランダム名のファイルを使い、そのファイル記述子経由で書き込みと権限設定を行うこと。既存パスへの `Lstat` 確認を追加するだけでは、確認後の差し替えを防げない。書き込み・クローズ・置換のエラーを処理し、安全に作成した一時ファイルだけを片付ける。

修正後は、旧形式の一時ファイル名にリンクや通常ファイルがあっても、その内容・権限が変化せず、共有ファイルが通常ファイルとして保存されることを回帰テストで確認する。

### SEC-002 暗号鍵なしでルームの接続枠と添付件数を消費できる

初回調査時は未修正。現在はPR #74で修正・マージ済み。CWE-306 / CWE-400に相当する。本文の復号や編集権限の突破は確認していない。可用性に対する問題である。

対象は [packages/worker/src/index.ts](../../packages/worker/src/index.ts) の35〜64行、および [packages/worker/src/room.ts](../../packages/worker/src/room.ts) の55〜68行、123〜136行、140〜177行。

WebSocketはホストのBearerトークンだけを検証する。ゲストは暗号鍵の所持確認なしで接続枠に加算され、無通信でも接続できる。添付APIはルームIDとblob IDの書式、およびホスト接続の有無を確認するが、書き込み側の参加資格は確認しない。blob IDが正規のHMAC値であることもサーバーは確認していない。

そのため、暗号鍵を知らなくても次の操作が可能である。

- ホスト1接続に加えて31接続を開き、`MAX_PEERS = 32` を満たすと、その後の正規参加者はHTTP 429で拒否される。
- 異なる任意の22文字blob IDへ空のPUTを送り、添付件数を消費できる。`Content-Length: 0` は許可され、サイズ0でも件数は1増える。既定の500件に達すれば、そのセッションでの新しい添付は429になる。

ルームIDは推測困難だが、秘密の暗号鍵とは違ってURLパスに含まれ、リレーや経路上のログに現れ得る。また、フラグメントを除いたURLを知る相手にも分かる。今回、実際のログ流出を確認したわけではない。Cloudflare Accessで全経路が保護されていれば、攻撃者にはそのAccessを通過できることも必要になる。

再現は [worker.test.ts.txt](repro/worker.test.ts.txt)。Cloudflareのローカルテストランタイム上に新規ルームを作り、ホスト接続後、暗号鍵を一度も生成しないクライアントから接続とPUTを行った。ホストトークンはセットアップのホスト接続だけに使用した。

- 31本のゲスト接続後、新規接続は429となった。
- テスト設定の件数上限3に対し、空のPUTが3回とも201となり、次の1バイトのPUTが429となった。
- 本番既定の500件については同一カウンター処理からの評価であり、本番環境に500回PUTしたわけではない。

修正案は、暗号鍵とは別の参加用認証情報を導入し、WebSocket枠の確保とblob書き込みの両方で検証すること。参加用情報を共有リンクのフラグメントに保持し、ホストがその検証情報を登録するなど、暗号鍵そのものをサーバーに渡さない設計にする。未認証接続の短い期限、接続・書き込み回数制限、ホスト用の接続枠予約も併用する。空のblob拒否だけでは、有効な長さのダミーデータで件数を消費されるため十分ではない。

修正後は、ルームIDのみの相手が接続枠・添付件数を消費できず、参加用認証を通過した相手は利用できること、暗号鍵がHTTPリクエストやログに送られないことを回帰テストで確認する。

### SEC-003 新規保存ファイルがumaskを無視して他ユーザーにも読める権限になる

初回調査時は未修正。現在はPR #75で修正・マージ済み。CWE-732に相当する。SEC-001とは独立し、シンボリックリンクを必要としない。

その後、SEC-004の修正（PR #78）で加わった `BoundFile.Write` が、新規ファイルにも作成後に0600を `Chmod` していた。参加コピーと、共有中に削除された共有ファイルの作り直しでは、umaskによる追加の制限が効かず常に0600になっていた。group/otherに権限が付くことはない。[#118](https://github.com/piconic-ai/pedit/issues/118) で、既存ファイルのときだけ `Chmod` するよう修正した。

対象は [internal/filewriter/filewriter.go](../../internal/filewriter/filewriter.go) の19〜28行、[internal/attach/attach.go](../../internal/attach/attach.go) の354〜361行。新規の参加コピーへの呼び出し経路は [internal/session/join.go](../../internal/session/join.go) の203〜238行。

`WriteAtomic` は保存対象が存在しない場合に0644を選び、作成後の `Chmod` でumaskによる制限を解除する。添付保存も `os.CreateTemp` の0600を最後に0644へ広げる。そのため、`umask 077` を設定しているユーザーでも、新規の共有本文コピーや保存された添付にgroup/otherの読み取り権限が付く。

例えば、他ユーザーが参照可能な既存ディレクトリを `pedit '<共有リンク>' -d <dir>` の保存先にすると、共有内容の平文が他のローカルユーザーにも読める権限で作成される。添付の場合も、既存の `assets` と親ディレクトリが参照可能なら同様である。読み取り可否には親ディレクトリの権限やACLも関係する。既定のCLI参加先は0700の一時ディレクトリなので、その設定では外側のディレクトリによって保護される。また、既存0600本文の通常更新はそのモードを維持する。

再現は [filewriter_test.go.txt](repro/filewriter_test.go.txt) の `TestSecurityAuditNewFilePermissions` と [attach_test.go.txt](repro/attach_test.go.txt) の `TestSecurityAuditAttachmentPermissions`。シェルを `umask 077` にして実行し、対照の通常ファイルが0600で生成されることを確認したうえで、新規本文と添付の保存ヘルパーが0644を返すことを確認した。添付の検証は合成データで保存処理を直接呼び出しており、画像のアップロード全体を再現するテストではない。他のOSユーザーとして実際に読み出す試験はしていない。

修正案は、新規ファイルを原則0600とし、明示的な設定がある場合だけ権限を広げること。既存ファイルのモード維持と新規ファイルの作成モードを別に扱い、新規ファイルへ0644を無条件で `Chmod` しない。添付も少なくとも共有元ファイルより広い読み取り権限を付与しない方針を決める。

修正後は、umask 077と参照可能な既存保存先を組み合わせ、新規本文・添付にgroup/otherの読み取りビットが付かないこと、および既存本文の権限を維持することを確認する。

| SEC-004 | 中 | 監視中の共有パスをsymlinkに差し替えると、共有対象外のファイルを参加者へ送信する | ローカル攻撃者が共有パスを置換でき、CLIユーザーがリンク先を読める。取得にはルームの参加者であること、または参加者との協力も必要 |

| SEC-006 | 中 | ルーム作成時のリダイレクトがCloudflare Accessトークンを別オリジンへ転送する | Access認証付き作成リクエストが、意図しない送信先へのリダイレクトを受ける |

別途、開発用npm依存に既知脆弱性の警告11件と、Go依存に脆弱なバージョン1件を確認した。これらは下記で到達可能性を区別して記録する。

### SEC-004 監視対象のsymlink差し替えによる共有対象外ファイルの送信

再調査時は未修正。PR #78で修正実装済み。CWE-61 / CWE-200に相当する。

対象: `internal/filewriter/filewriter.go:38`、`internal/session/session.go:393`。`watch()` は共有ファイルと同名のファイルシステムイベントで再読込を予約し、`syncFromDisk()` は `readSettled()` → `filewriter.ReadFile()` → `os.ReadFile()` で内容を取得して文書へマージする。`os.ReadFile()` はシンボリックリンクを追跡する。

共有ファイルを削除・置換できるローカル攻撃者が、そのパスをCLIユーザーにだけ読める別ファイルへのsymlinkに変えると、リンク先の内容が通常のローカル編集として暗号化され、現在の参加者へ送信される。リンク先の書き込み権限は不要。ファイルの0600は、権限を持つCLI自身が読み出すことを防がない。

これは前回SEC-001の予測可能な一時ファイルを使う上書きとは別の読み出し経路であり、今回の `CreateTemp` 修正を迂回して一時ファイルを操作するものではない。

再現: [session_test.go.txt](repro/session_test.go.txt) の `TestSecurityReauditWatchedSymlinkSharesOutsideFile`。

1. 通常の本文を共有するホストとゲストを起動し、初期同期を確認。
2. 共有ディレクトリ外に、合成の秘密本文を持つ0600ファイルを作成。
3. 共有パスをそのファイルへのsymlinkに置換。
4. 実際のfsnotifyによる再読込後、ゲストの文書が秘密本文になったことを確認。リンク先の内容自体は変更されない。

race検査付きでPASS。テストは同一UIDで攻撃操作を模擬しており、別OSユーザーでの侵入実験ではない。攻撃者には親ディレクトリの権限等により共有パスを置換できることが必要で、リモート参加だけでは成立しない。

修正方針: 開始時に共有対象の基準となるディレクトリとファイルを確定し、再読込時もsymlinkやreparse pointを経由した別対象への切替を拒否する。`Lstat` 後に通常の `ReadFile` を行うだけでは競合が残るため、ディレクトリハンドルを基準にしたopenとno-follow、開いた記述子への検査を組み合わせる。通常のエディターによる一時ファイルからのrename保存は維持する。保存前の衝突確認や終了時の再読込にも同じ境界を適用する。

回帰条件: 上記の差し替えで文書・ゲストに秘密本文が入らず、安全なエラーとして扱えること。通常のrename保存、最終保存、明示的にsymlinkを共有する場合の方針もテストする。

### SEC-005 共有されていない兄弟画像の再送

再調査時は未修正。PR #79で修正実装済み。CWE-862 / CWE-200に相当する。

PR #79の[追加レビュー](https://github.com/piconic-ai/pedit/pull/79#pullrequestreview-5414776136)で、1文字の区切りで隣接する参照の2件目を抽出できず、隣の参照をローカルで削除すると未許可画像が新規参照として許可される回避経路が見つかった。マージ後の追加修正では、参照候補を列挙して前後の境界を別に検査する方式に変更した。空白・改行・句読点などで隣接する参照の抽出と、リモート挿入→ディスク保存→隣の参照だけをローカル削除→再同期→添付要求のセッション回帰テストを追加し、画像がアップロードされないことを確認した。

対象: `internal/attach/attach.go:224`、同 `:376`。`wanted()` は受信したハッシュを `load()` に渡す。`load()` は同じディレクトリの `assets/<hash>.<ext>` を検索し、通常ファイル・サイズ・内容ハッシュ・画像種別を検証するが、現在共有している文書に属する画像かを確認しない。

そのため、同じassetsを複数の文書・セッションで共用していると、文書Aだけを共有した参加者が、文書Bの画像のハッシュを指定して取得できる。対象画像が現在の文書に記載されていなくても、現在のルーム鍵で再暗号化してblobへアップロードされる。暗号化と参加認証は通過しており、問題はホストが読み出しを許すローカルファイルの範囲にある。

再現: [attach_resend_test.go.txt](repro/attach_resend_test.go.txt) の `TestSecurityReauditUploadsUnreferencedSiblingAsset`。

1. 画像へのリンクを一切含まない共有文書を作成。
2. 同じassets内に、他の文書由来を模した合成PNGをハッシュ名・0600で事前配置。
3. そのハッシュだけを持つ `AttachmentWant` を受信処理へ渡す。
4. `AttachmentAnnounce` が送信され、blobの内容を現在のルーム鍵で復号すると元のPNGと一致する。共有文書は変更されていない。

race検査付きでPASS。この検証は添付ハンドラーからローカルblobサーバーまでを通すもので、この要求を本番WebSocketへ送ったわけではない。

任意パスや任意ファイルを読めるという報告ではない。対象は所定の拡張子と内容ハッシュが一致するassets内の画像に限定される。128-bitのハッシュを無差別に推測することは現実的ではなく、別のMarkdown、ファイル一覧、過去の共有などからファイル名を知っていることが前提となる。

修正方針: ホストが共有を許可した画像の集合を持ち、再送前に照合する。例えば、開始時にホストの文書から参照されていた画像、ホストがローカルで追加した画像、そのルームで正規に保存した画像を登録する。リモート参加者が編集できる現在の文書だけを毎回根拠にすると、攻撃者がリンクを追加して許可範囲を広げられるため不十分。文書ごとにassetsを分離する設計も選択肢となる。

回帰条件: 無関係な既存画像にはアップロードもannounceも発生せず、共有対象の既存添付と当該セッションで保存した添付の再送は成功すること。

### SEC-006 ルーム作成リダイレクトでのAccessトークン転送

再調査時は未修正。PR #80で修正実装済み。CWE-201 / CWE-522に相当する。

対象: `internal/session/session.go:277`。`createRoom()` は `Cf-Access-Token` を含むヘッダーを付けて `client.Do(req)` を呼ぶが、リダイレクト制約を設定していない。通常CLIのAccessログイン後もこの経路を通る。前回修正でWebSocket接続・添付HTTP通信はリダイレクト拒否になったが、ルーム作成は対象外だった。

GoのHTTPクライアントは既定でリダイレクトを追跡し、一部の特別扱いするヘッダーを除いてヘッダーを転送する。独自ヘッダーである `Cf-Access-Token` は、異なるホストやHTTPSからHTTPへの遷移でも転送される。[Go公式Client仕様](https://pkg.go.dev/net/http#Client)

再現: [session_test.go.txt](repro/session_test.go.txt) の `TestSecurityReauditCreateRoomRedirectLeaksAccessHeader`。

- ローカルHTTPSサーバーで `POST /api/rooms` を受け、別ホスト名のローカルHTTPサーバーへ307を返した。
- 実際の `createRoom()` に合成Accessトークンを渡し、転送先が同じトークンを受信したことを確認した。
- TLS検証はhttptest専用クライアントがテスト証明書を信頼する形で行い、実トークンは使用していない。

race検査付きでPASS。認証情報を転送する挙動の再現であり、本番に攻撃者が操作可能なオープンリダイレクトがあることを確認したものではない。実際の漏えいには、意図しない転送先を返す設定・プロキシ・リダイレクト経路が必要。トークンの再利用可能期間・権限はAccess側の設定に依存する。

修正方針: 認証ヘッダーを持つルーム作成リクエストは自動リダイレクトを拒否する。Access未ログイン判定は302等の `Location` を追跡せずに判定するなど、既存ログイン導線を維持する。共有のHTTPClientを直接変更せず、添付と同様にコピーしたクライアントへポリシーを設定する。

回帰条件: 別オリジン・HTTPS→HTTPへの302/307/308で転送先が認証ヘッダーを受け取らず、Accessログイン検出と通常のルーム作成が成功すること。

### 依存関係の確認

監査出力の要点と該当バージョン・経路は [dependency-audit.json](repro/dependency-audit.json) に保存した。以下は更新前の監査結果であり、修正版への更新はPR #81に含めた。

`pnpm --dir packages audit --json` は11件（high 3、moderate 5、low 3）を報告した。`pnpm --dir packages audit --prod --json` は0件。警告の経路は開発用 `@cloudflare/vitest-pool-workers` → Miniflare の `sharp 0.35.2` と `undici 7.29.0`。別のWrangler → Miniflare経路にも `undici 7.29.0` がある。ロックファイルの該当箇所は `packages/pnpm-lock.yaml:3425` 付近。

- sharpの[公式アドバイザリー](https://github.com/lovell/sharp/security/advisories/GHSA-rgj7-g3m4-5g8c)は、特定のLinux環境で不正なHEIF/AVIF入力を処理した場合の危険性と、0.35.4への更新を案内している。本アプリはWorker側にImagesバインディングを持たず、画像処理はブラウザーで行うため、本番画像アップロードがこのsharpを呼ぶ経路は確認していない。
- undiciには複数の警告がある。一例の[公式WebSocketアドバイザリー](https://github.com/nodejs/undici/security/advisories/GHSA-rfgv-xxqx-mfg5)では、不正なハンドシェイクでNodeプロセスが終了し得ることと、7.29.1への修正が示されている。npm監査の件数はアプリ内での攻撃成立件数ではない。各APIの利用条件に照らした検証は未実施。

これらは開発・CI環境の依存更新課題として扱い、本番にhighの脆弱性が3件あるとは判定していない。互換性を保ってCloudflareのテストツール群を更新し、ロックファイルと既存テストを再検証する。

`govulncheck v1.8.0` をGo 1.27.1で実行。macOS向けと `GOOS=windows GOARCH=amd64` の両方で、脆弱な関数への到達を示すfindingはなかった。`golang.org/x/sys v0.35.0` に [GO-2026-5024](https://pkg.go.dev/vuln/GO-2026-5024) のバージョン一致があり、Windows解析ではパッケージの使用まで検出したが、問題の `NewNTUnicodeString` 呼び出しは検出されていない。修正バージョンはv0.44.0。将来の利用追加も考慮した更新候補だが、今回の実証済み課題3件には数えていない。配布済み全バイナリや異なるGoバージョンでの解析は実施していない。
